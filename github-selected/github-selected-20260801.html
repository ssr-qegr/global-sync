1. google/adk-python

Google 开源的 Agent Development Kit：把构建、编排、运行、评测与部署 Agent 的核心能力整合到同一套框架里

TOP 1
🧠 Code-first🕸️ Graph Workflows🤝 Multi-Agent🧪 Evaluation📈 Observability🖥️ CLI / Web / API

项目详细介绍：ADK 可以理解成一套面向工程实践的 Agent 开发框架。它不是只帮你定义一个 Agent，而是试图把从 Agent 结构设计、工作流编排、任务委派，到运行时、部署、评测和安全边界这整条链路都放在统一模型里。官方仓库把它定义为一个开源、code-first 的 Python 工具包，用于构建、评估和部署复杂 AI Agent；文档结构则进一步说明它支持 Graph Workflows、Multi-Agent Workflows、Runtime、Deployment、Observability 和 Evaluation，说明这个项目的目标是“让 Agent 能长期运行与演进”，而不只是做个 Demo。

技术亮点

  • 图式工作流很完整：ADK 2.0 引入 graph-based execution engine，支持路由、fan-out / fan-in、循环、重试、状态管理、动态节点、人类介入和嵌套工作流，适合处理复杂任务链路。
  • Task API 适合做 Agent 协作：官方把 agent-to-agent delegation 做成了结构化能力，既支持多轮任务模式，也支持单轮受控输出，还能把 task agents 直接作为工作流节点。
  • 运行方式覆盖完整：除了代码定义 Agent，还能通过 CLI、Web UI 和 API Server 跑起来，对调试、联调和对外服务都更友好。
  • 工程配套较成熟：文档里单独列出了 Deployment、Observability、Evaluation 和 Safety & Security，说明它考虑的是长期维护，而不是一次性实验。
  • 模型和集成面广：官方文档明确覆盖 Gemini、Claude、OpenAI、Ollama、vLLM、LiteLLM 等模型接入路径，更适合做跨模型的 Agent 系统。

使用场景

  • 内部智能助手或工作流 Agent：当你需要把多个子 Agent、工具调用和人工确认串成完整流程时，图式工作流会非常有价值。
  • Agent 平台原型搭建：如果你想快速验证“一个框架能不能同时承接开发、调试、运行和部署”，ADK 很适合作为统一底座。
  • 多 Agent 协作场景：需要任务拆解、角色协作、节点编排和可恢复运行时，这类框架比手写 orchestration 更稳。
  • 评测与可观测要求较高的 AI 应用：如果你已经开始关心日志、指标、评估和运行质量，ADK 的文档结构很值得借鉴。

为什么今天推荐它

  • 很多人已经会“做一个 Agent”，但真正稀缺的是“把 Agent 做成系统”的能力。
  • ADK 值得看的地方不只是 Google 背书，而是它把工作流、运行时、评测和部署视作同一件事来设计。
  • 如果你未来想做企业内 AI 助手、流程自动化 Agent 或多 Agent 系统，这个项目非常适合作为方法论参考。

2. firecrawl/firecrawl

把 Search、Scrape、Interact 合成一条链路的 Web Context API：为 Agent 提供更稳定、更易消费的网页数据入口

TOP 2
🔎 Search🕷️ Scrape🖱️ Interact📄 Markdown / JSON🔗 MCP Ready🌐 Crawl / Map

项目详细介绍：Firecrawl 不是普通的爬虫仓库，它更像“专门为 AI 应用设计的网页上下文层”。官方仓库把它定义为一个可在大规模场景下搜索、抓取并与网页交互的 API，目标是把网页来源、正文抽取和结构化输出统一成更适合 Agent 使用的能力。官方文档首页则把核心能力拆成 Search、Scrape、Interact：先搜到来源，再把页面转成 markdown / HTML / structured JSON，必要时还可以继续点击、填写、等待或抽取动态内容。对做 RAG、Deep Research、竞品情报、网页自动化的开发者来说，这种统一设计非常实用。

技术亮点

  • Search / Scrape / Interact 一体化：很多团队的问题不是不会爬，而是搜索、抽取、交互和二次处理分散在多套工具里，Firecrawl 把这条链路整合得更适合 Agent 直接调用。
  • 输出天然面向 LLM：官方持续强调 clean markdown、structured JSON、screenshots 等结果形式，这比原始网页源码更适合进入上下文窗口或后续结构化处理。
  • 处理动态网页的能力强：文档明确提到 proxies、anti-bot、JavaScript rendering 和 dynamic content，这正是很多 AI 应用接网页时最头疼的部分。
  • 对 Agent 生态友好：官方仓库和文档都强调 MCP Server 与 CLI 路线，说明它并不是只想做一组 API，而是想成为 Agent 的标准网页工具层。
  • 能力边界不只停留在单页：除了核心三件套，它还覆盖 Crawl、Map、Batch Scrape、Agent 等延展能力，更适合做成持续的数据管道。

使用场景

  • RAG 与知识库构建：把文档站、博客、帮助中心或公开页面转成更干净的 markdown / JSON，方便后续切片与索引。
  • Deep Research 与信息采集：先搜索，再抽取，再继续打开和交互页面，比传统“只返回搜索结果链接”的工具更完整。
  • 网页自动化前的数据获取：当页面需要点击、滚动、等待或填写后才出现有效信息时，这类交互能力会非常重要。
  • 给现有 Agent 补网页能力：如果你已经有 Agent，但缺少稳定的 Web Context 输入层，Firecrawl 是很直接的补强方案。

为什么今天推荐它

  • 很多 AI 应用上线后效果不好，不是模型不行，而是喂进去的网页上下文太脏、太碎、太不稳定。
  • Firecrawl 值得学的地方，不只是“会爬网页”，而是它如何围绕 Agent 重新组织网页数据入口。
  • 如果你最近在做研究助手、搜索增强、网页采集或自动化信息流，这个项目很值得深入看。
